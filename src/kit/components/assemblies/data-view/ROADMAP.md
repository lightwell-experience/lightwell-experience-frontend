## Why this family exists

`assemblies/data-view/` holds **list/collection table surfaces** — toolbar
(filters + pagination) and table (DataView root + active-state wiring). Product
pages configure them; they do not own fetch or domain catalogs.

This family is **not** new ground: `@patternfly/react-data-view` is already used
by Lightwell's `src/Pages/Lightwell/Lens/components/PackageCoverageTable.tsx`,
alongside a shared `src/Hooks/tables/useTableActiveState.ts` hook and
`src/components/EmptyTableDataView/EmptyTableDataView.tsx`. This family
**generalizes that call site into kit units** — it does not invent new
DataView usage.

**Reference architecture:** the
[PF data-view extension](https://www.patternfly.org/extensions/data-view/overview#modularity)
defines the modular architecture: `DataView` (root stack) + `DataViewToolbar`
(header/footer) + `DataViewTable` (data representation) + `DataViewFilters`
(toolbar filter controls). The kit wraps these as `LwDataView` +
`LwDataViewToolbar`. The drawer is Lightwell's addition — an opt-in container
shell that can hold filter panels, detail views, or any content.

**Non-destructive:** product wiring **replaces** call sites by swapping in
kit units. Existing domain components stay until each replace lands, per the
migrate/dissolve convention in
[`kit/examples/dissolution-map.md`](../../../../../.cursor/skills/kit/examples/dissolution-map.md).

## Table unit (`LwDataView`) — reference

`data-view.tsx` is a flat family-root file (the "exception to the rule" —
same shape as `assemblies/page/page-chrome-slots.tsx`), so it carries no
separate unit `README.md`/`ROADMAP.md` pair. Its unit-level reference lives
here instead.

**Why it exists:** full data-view surface so product pages get PatternFly's
DataView pattern with Lightwell-specific defaults baked in, instead of each
page configuring `@patternfly/react-data-view` from scratch: non-compact
density by default, native sticky-column/header support, named slots for the
outer `DataView` host, and an opt-in inline drawer shell.

**Host:** `@patternfly/react-data-view`'s `DataView` + `DataViewTable`.
Generalizes the pattern already used by
`src/Pages/Lightwell/Lens/components/PackageCoverageTable.tsx`. Prop defaults
flow through `components.config.ts`'s `dataView` entry via `mergeComponentProps`.

**API:**

```tsx
import { LwDataView } from 'kit/components/assemblies';
import { LwForm, LwCheckbox } from 'kit/components/primitives';

// Built-in toolbar — pass data, LwDataView builds the toolbar (D12/D18 shape)
<LwDataView
  aria-label='Vulnerabilities'
  columns={columns}
  rows={rows}
  isLoading={isLoading}
  emptyState={{ titleText: 'No results found', onClearFilters: resetFilters }}
  search={{ value: searchValue, onChange: onSearchChange, placeholder: 'Filter by...' }}
  pagination={{ itemCount: count, page, perPage, onSetPage, onPerPageSelect }}
  panelToggle={{ isExpanded: isPanelOpen, onToggle: togglePanel }}
  panel={<LwForm aria-label='Filter categories'>{/* LwCheckbox groups */}</LwForm>}
/>;
```

The older shape — an explicit `<LwDataViewToolbar>` child instead of
`search`/`pagination`/`panelToggle` props — still works (Lens, Repositories,
Packages use it today) but is superseded; see D18 (held until D17's filter
capability ships, so the three consumers move once, not incrementally).
